# Active evaluation: one task family

This document implements the [narrow training and inference protocol](11-narrow-training-and-inference.md). The previous multi-family bootstrap and multi-surface gate are preserved as an [inactive expansion reference](future/evaluation-broad-reference.md). They do not apply to the current pilot.

**Implementation boundary:** this document specifies the native pilot gate. The current [repair-scoring component](17-repair-scoring.md) implements a smaller synthetic development comparison and never promotes a package. All three native variants in the recorded initial baseline have already been exposed; none can now serve as a fresh sealed instance. The sealed-data rules below require genuinely unexposed instances before that gate can be claimed.

**What is evaluated.** Use one complete native AppWorld scenario, its three native variants, the pinned environment and official terminal evaluator. Restrict exposed business APIs to the selected family while retaining required setup/completion APIs and the entire native objective. Record the chosen episode limits as experimental settings. Fault injection and generated variations are separate conformance/stress cases, never counted as native benchmark successes.

**Instance roles.** All three start in the official train split. A stored seeded ordering assigns one fit instance, one development instance and one sealed check. Preserve both original split and internal role in every manifest. Fit/development evidence can guide repairs. The improver cannot see the sealed instruction, state, trace or score before the chosen candidate is frozen. The actor sees that task's permitted instructions only when it is actually evaluated.

Three fresh-environment repeats measure consistency on each instance. They do not create three new tasks. Do not compute family-clustered confidence intervals or claim cross-family generalization from a single family. Native scenario completion is reported only when all required native variants have actually been evaluated; fit-only subset results are not a full-scenario metric. Keep AppWorld's native evaluator output unchanged. [Official evaluator](https://github.com/StonyBrookNLP/appworld/blob/42b5bcf3cd334fee33f0c37c02070a9f5807add5/src/appworld/evaluator.py#L322).

**Baseline and candidate order.** First run A, raw-tool ReAct through the kernel. If a reproducible failure warrants a typed helper, evaluate B with ordinary records. Only then, when there is a concrete graph hypothesis, evaluate C with the same helper interface and graph operators. Optional B/C variants consume the same three-candidate repair allowance; each does not receive a fresh search budget. Select a candidate from visible fit/development results, freeze it, then compare it with its parent on the sealed instance. Do not use sealed outcomes to choose between A/B/C after the fact.

Pair runs by instance, repeat and environment seed. Alternate parent-first and candidate-first using a recorded hash. Use the same CLI configuration, authority, available source data, episode bounds and declared warmup. Different context/abstraction is an explicit experimental variable, not hidden extra evidence. Count all internal API and extraction calls. Capture any unobservable provider context/usage as a limitation.

**Local acceptance gate.**

1. Reject any candidate that changes protected code, bypasses admission, reaches evaluator secrets, fabricates a trace or introduces an unresolved effect. All applicable control fixtures must pass, including known-valid calls; deny-all cannot qualify.
2. Require an independent deterministic reproducer of the target failure and preserving cases. A diagnosis alone is insufficient. For a graph implementation, require a preregistered computation/provenance/update-handling advantage or retain the simpler row implementation.
3. Require the candidate to pass all three scheduled repeats of each visible instance before the frozen check. Existing applicable conformance cases must remain passing. Retain any partial improvement in the archive without labeling it ready.
4. Evaluate the frozen candidate and parent on the sealed instance, three repeats each. Require candidate three-of-three native passes, no control/integrity failures, and no observed regression against the parent. If it fails, report the failure and do not tune on that same check while preserving a sealed-data claim.
5. Require the recorded mean step/tool/wall ratios to remain within the profile's 1.20 budget relative to the parent, except where the parent never achieved a valid task result. In that latter case report resources and enforce absolute episode bounds, since a short failed run is not a meaningful efficiency target. With zero parent use, equal zero has ratio one and positive candidate use has infinite ratio.
6. Promote only to the local one-family experimental baseline and label the gate `NARROW_PILOT_ACCEPTANCE`. This is an engineering release rule over nine candidate runs, not statistical proof of robust transfer.

If the unchanged baseline already passes and no supported defect exists, there is no obligation to generate a repair or add a graph. If model/capability failures prevent a scored run, report unavailable rather than assigning a fabricated task score. A missing scheduled result blocks acceptance; all starts, failures and bounded infrastructure reruns remain visible. Allow at most one infrastructure rerun for a predefined infrastructure code, linked to the original. Model mistakes are not infrastructure failures.

A consumed sealed check is retired. Further tuning may use it as development, but a future fresh check needs genuinely new same-family data. Versioned-generator instances are explicitly labeled generated; their source, seed and independent evaluator must be recorded. If new instances are unavailable, retain the restricted evidence claim instead of pretending another stochastic rollout is a new held-out task.

**What success means now.** The actor executes this small workflow under enforced contracts; authorized work remains possible; finish claims are checked; repeat/denial/revisit cases terminate honestly within bounds; every effect has a receipt; and a supported repair can be tested and accepted or rejected reproducibly. An observed nine-of-nine result is reported exactly as that. Demonstrated repair gain requires an actual fixed failure or a preregistered measured benefit. A second surface and long-context curriculum are not completion requirements.

**What learning produces.** Fixed-weight package learning produces an immutable mapping/function/interface patch or an independently justified schema correction, linked to its source failures and tests. The target is reusable handling of relationships and task constraints, as defined in the [computational protocol](12-computational-learning-protocol.md). Store all failed attempts. Positive imitation exports include only verified actor decisions and recovery continuations with their original context; do not relabel rejected actions or kernel-corrected arguments as successful actor output. The native evaluator supplies task success, the deterministic checks supply control facts, and the judge supplies advisory mechanism diagnoses.

Weight training is deferred. It would require a trainable checkpoint and separate tokenization, dataset, optimizer and evaluation protocol. The current configured CLI remains the inference interface and receives the frozen selected package on every test episode.
