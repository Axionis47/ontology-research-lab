# Failure-driven repair, code onboarding and release

Repair runs between episodes. Active episodes retain their package hash. The trusted kernel, operator membership/runtime, evaluator, budgets, trace instrumentation, sandbox and promotion rules are locked. In the active [computational protocol](12-computational-learning-protocol.md), automatically editable surfaces are source mappings, typed function implementations, function I/O contracts and independently justified domain schema changes. The primary learning target is reusable handling of relationships and constraints. Current task obligations, observed instance values, workflow suggestions and prompt/context prose are not automatic optimization targets. Runtime defects are engineering issues with reproducer evidence, not an excuse for the repair model to weaken controls.

**Current scale:** the [narrow protocol](11-narrow-training-and-inference.md) limits this machinery to one family, one candidate per cycle, three visible cycles, two changed files and four proposer calls per candidate. No package is required before the raw-tool baseline. The larger search counts in this reference describe expansion only; active profile limits and the narrow evaluation gate apply now.

Diagnosis, repair, build and comparison each run as a bounded offline job from document 01. Each job has a manifest, model/operation receipts, append-only events and a terminal outcome. Inputs may link several completed training episodes. The job's spending is charged to its experiment subaccount, not a reset or reopened episode. A failed job is archived even when no candidate patch is produced.

**Failure selection.** After training evaluation, group supported findings by `(requirement category, responsible component, mechanism, package version)`, not just exception text. Retain original event IDs. Sort by severity, count of affected distinct task families, then oldest unresolved finding ID. Exclude pure infrastructure/authentication failures and cases without enough evidence to distinguish a proposed cause. Select one mechanism per candidate. Include at least one passing analogous behavior that the repair must preserve.

**Consolidation before repair.** Follow [the consolidation contract](12-computational-learning-protocol.md#consolidation-before-repair) before issuing a patch request. Discover existing scoped entity identities, schema definitions, mappings and functions through bounded, recorded queries. Distinguish a missing observed edge from a mapping gap, a composition gap and a genuinely missing definition. Reuse existing IDs and definitions where evidence supports the match. Attach discovery receipts and the handoff/continuation/outcome lineage to the repair evidence. Partial lookup, ambiguous identity or unsupported relationship claims require more evidence; they cannot justify inventing types or edges. A fact-ingestion update is separate from a reusable package repair. The discovery store and consolidation worker are still pending implementation.

**Repair specification.** The planner emits a `RepairSpec` containing: parent package hash; finding/evidence IDs; exact faulty behavior; proposed mechanism; allowed files/JSON paths; prohibited changes; smallest reproducer; expected output/postcondition; preservation examples; applicable regression suite; patch size/file limits; build environment/dependency lock; evaluation schedule; and stop conditions. A diagnosis without a distinguishing test becomes `NEEDS_EVIDENCE`, not a code-generation request. The expected result must come from an independently specified contract/fixture, not solely the judge's preference.

**Patch generation.** Give the configured CLI the repair spec, allowed source excerpts, reproducer, relevant contracts, preserving examples and past rejected patch signatures. The CLI has no task execution tools. It returns a structured unified diff plus a `CandidateManifest`. Limit to three changed files and 32 KiB of patch bytes; larger repairs become separately scoped engineering work. Up to eight metered model calls may fetch bounded source excerpts through the evidence gateway, propose and correct a patch. No open-ended autonomous shell session is part of this stage.

**Code onboarding, step by step.**

1. Materialize the exact parent package into a new candidate directory. Verify all file hashes and the runtime/dependency lock before applying anything.
2. Validate the manifest and patch. Reject absolute paths, `..`, symlink escapes, binary files, undeclared files, dependency changes, protected-rule edits and generated test/evaluator substitutions. Normalize line endings only under a recorded transform.
3. Apply the patch to staging. A conflict returns `PATCH_INVALID` with bounded context. At most one correction request for that conflict, inside the eight-call limit; do not silently edit around a conflict.
4. Parse schema/mapping/workflow files, check referential integrity, compile Python, type-check public signatures, and check declared tool/operator effects. Reject undeclared imports or dynamic dependency loading before execution. These checks are diagnostics; the sandbox still enforces access.
5. Build an OCI candidate image from the pinned runtime and locked dependencies without network access. Store the resulting image digest, source hash and build log. New third-party dependencies require a separate engineering change, outside automatic repair.
6. Run the minimal reproducer, preservation fixtures, malformed/missing-value cases and full kernel conformance suite in isolated environments. Judge-generated tests may add coverage but cannot replace existing checks. Their expected outputs require the contract/source basis recorded in the repair spec.
7. Execute paired target and broader train/dev episodes with the frozen actor, tool authority, budget, task/seed schedule and fresh environment instances. Preserve all results, including build errors, timeouts and failed attempts. Do not edit the candidate during evaluation.
8. Archive the candidate, diff, all model/build/test receipts and evaluations. Decide exploration retention and formal promotion separately using document 08.

A candidate has lifecycle `PROPOSED → PATCHED → BUILT → CONFORMANCE_PASSED → EVALUATED → ARCHIVED`. Failure at any stage is terminal for that candidate ID, with a reason. A corrected patch is a new child candidate and consumes the remaining cycle allowance. The archive retains rejected material under appropriate visibility.

**Bounded research loop.** Start from the seed or a retained candidate. Evaluate at most three proposals per cycle. A retained parent must pass conformance and show a target improvement without observed train/dev regressions under the fixed comparison; otherwise keep the previous parent. Tie-break by lower metered resource use then smaller patch. Exact normalized patch/package hashes prevent duplicate evaluation. Semantically similar mechanisms are flagged from structured finding/changed-symbol signatures; no claim that a heuristic proves novelty.

Stop search after two cycles without a retained train/dev improvement, ten total cycles, or exhaustion of the experiment's allocated budget. Record `SEARCH_STALLED` or the appropriate limit. This is a research stopping rule, not a task-success claim. A stalled search can keep a valid current system while reporting that no improvement was demonstrated.

**Narrow promotion.** A training parent is not the active inference package. Choose and freeze one candidate from fit/development evidence before comparing it with the parent on the sealed third instance. Use document 08's local acceptance gate. No candidate reselection follows that sealed feedback. Retire an exposed check; future fresh-holdout claims need new same-family instances. A local acceptance label does not establish cross-family transfer. The broader archived evaluation protocol applies only if that scope is later reopened.

For a qualifying package, perform an atomic registry compare-and-set from the expected active hash to the promoted hash and append the gate receipt. Only new episodes use it. A failed compare-and-set means another release occurred; recompute the comparison against the actual active parent, never overwrite blindly. Rollback changes the pointer for future episodes and records why; existing traces and affected outcomes remain intact. Production deployment is outside this research release scope.

**Illustrative mechanism.** A mapping treats an absent `remaining_quantity` as zero, causing premature completion. The diagnosis cites the raw missing field, mapping branch, graph value and finish decision. The repair removes the fabricated default, represents unknown, and enables the existing authorized detail-read path. Tests distinguish missing from explicit zero and preserve complete-zero behavior. Success requires the failing input to recover, preserved cases to pass, no new unauthorized effects and the broader measured gate. Changing the judge to accept missing values would fail the protected-surface check.

The source inspiration is DGM's parent-linked candidate archive and isolated patch/evaluation cycle, together with HarnessX's bounded harness editing. This project adds explicit authority and promotion constraints; it does not inherit a safety proof from either repository. [DGM repair implementation](https://github.com/jennyzzt/dgm/blob/a565fd2d1dca504ef5104a7cc0f3bdc4ab9b4fd2/self_improve_step.py), [HarnessX evolver](https://github.com/Darwin-Agent/HarnessX/blob/ccb411691343d06b4a5c44c4e11104d694318e8f/recipe/tau2_evolver/run.py).

Completion evidence: one valid patch enters the archive with complete lineage; one protected edit is rejected; one superficially plausible regression fails measured evaluation; a qualifying gate fixture changes only the new-episode package pointer; an inconclusive real comparison leaves the active version unchanged.
