# Learning and demand-driven instantiation

## Semantic behavior revision

The semantic_v2 construction extension uses `oak.behavior` as the authoritative
behavior bank/compiler contract. The bank is generated from frozen TaskIR before
candidate S/F. It canonicalizes semantic dependency trees, merges repeated
question instances, retains observable scalar intermediates, and adds actual
parameterized point/property entry points. Uninterpreted requirements remain
explicit unknown behaviors in the fixed denominator.

The model supplies schema/source bindings and optional custom pure functions.
The compiler emits real FunctionSpecs and separate frozen acquisition bindings.
Actual tool contracts preserve native argument alternatives. Source arguments
for probes are recovered only through explicit templates and completed retained
receipts. A helper can start with empty G through its acquisition binding.

`oak.behavior_reference` separately interprets generated task semantics on genuine
retained graphs. Checks execute the actual bound candidate function. They record
observable result agreement, source entity IDs, actual execution evidence,
parameter/domain penalties and mutation sensitivity. Bounded code mutations
alter programs, never source records. A second labelled view of genuine retained
records can test a pure computation on another valid graph input; it is not a
claim that the view is a complete native response.

Mutation allocation is fixed by the bank, capped at eight per behavior and 64
per campaign. Missing bindings or selective replay cannot reallocate that budget.
Each behavior retains two input/evidence strata, including deferred and unknown
cases. Scoring does not count copied trajectories, duplicate checks, question
instances or renamed steps. Candidate ranking uses the independent verifier's
behavior report, penalties and counterexamples. Identical pure implementation
bodies share the size tie-breaker without removing callable entry points.

The supported semantic compiler covers reads, exact selectors, explicit numeric
and categorical filters, projection, numeric aggregates and scalar arithmetic.
Type, grain, domain and compatible-unit checks reject contradictions. Traversal
interpretations lacking a bounded endpoint-ID lowering remain uncompiled and
unknown, while supported custom runtime functions remain available separately.
Generated field-to-schema mappings remain proposed. A new mapping is not proof
that the mapped source field has the intended meaning. The separate verifier
must invalidate incompatible cached evidence and compare changed candidates on
the same retained source snapshot. No independent source-completeness or task-
truth claim follows from these generated checks.

The focused deterministic checks use portable retained weather artifacts and the
local genuine 5,746-record Coffee kernel. They demonstrate point access derived
from an aggregate task, smaller materialized slices, code-defect detection,
parameter-domain/dataflow penalties, source-template grounding and fixed scores
under duplicate questions/renamed steps. No paid call was made by this flow.

## Construction

`oak.learning_contracts` owns TaskIR and the typed task interpretation grammar.
The analysis stage receives every construction question, without development or
held-out inputs. TaskIR is frozen before schema/function proposals and records
literal requirements, mechanical observable-dependency closure, and at most 128
exploratory compositions with at most two added operators. Proposed meaning is
never automatically marked independently grounded.

The outer campaign invokes owned child construction runs. Each round uses
unseen-first seeded sampling, the existing schema/HermiT stage, real extraction,
function compilation, and actual function probes. Structural mapping errors are
repairable, while explicit unsupported behavior remains visible. Each candidate
has its actual parent revision. The learner consumes the verifier's report and
retains the best eligible candidate instead of blindly choosing the newest.

Model-generated consistency checks use the verifier's authoritative
GeneratedCheckSpec. The first useful candidate-referenced bank and genuine
source graphs are frozen for the campaign. Empty or standalone checks do not
prematurely freeze an unmeasurable bank. When a useful bank appears later, the
retained candidate is rechecked against it before comparison. Later candidates
cannot remove a failed check or substitute an easier one. A schema change
without a supported check translation is unknown.
Generated checks never become independent task-success evidence.

The configured bounds remain three rounds, 20% sampling, and two local repair
attempts. Function probe invocation bounds do not reset for another composition
repair. Fresh agent execution remains distinct from probe evidence and generated
consistency checks. Selection occurs after fresh runs and reruns the retained
candidate's previously observed cases. An independent failed assessment counts
as failure even when the agent says complete. Unexecuted comparisons are unknown.

## Instantiation

New kernels carry construction_profile=demand_v1. Historical artifacts remain
unchanged. For a new-profile inference, the executor derives an EvidenceDemand
from the chosen frozen function and its arguments. Extraction receives that
demand and emits only the needed records and schema-required dependencies.
Document accounting does not establish extraction completeness.

The episode records actual acquisition receipts by normalized capability and
arguments. Another computation can materialize additional properties from the
same receipt without repeating the MCP call. Materialization caching includes
the original receipt, kernel, extractor version, and normalized demand. Failed
or uncertain dispatch receipts are also remembered, preventing automatic repeat
of the same request. Existing graph merge conflict checks remain authoritative.
Acquisition functions use an isolated working graph for their own receipts, so
a prior location cannot contaminate a later aggregate. The episode graph retains
their union for inspection and pure helpers. Explicit source-document IDs
prevent receipt reuse from inflating document counts.

Evidence-scope observations distinguish missing values and uncertain population
coverage. The planner may expand through another frozen call, give a qualified
answer, clarify, or report unresolved within the existing budgets. Unknown scope
is not a completion veto. Independent evaluator results remain separate.
