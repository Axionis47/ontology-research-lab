# Historical execution replay and inference adoption

The active mechanism preserves original typed computations across an actual ancestry of immutable kernels. K1 cases execute on K3 through the shared E12 and E23 packages. Graph migration and call adaptation run forward; observable result adaptation runs backward. The current kernel's functions execute for real. Original outputs are comparison evidence, never replacement implementations.

This is a user extension to OaK. OWL/HermiT validity, graph integrity, historical computation preservation, generated consistency checks, and fresh planner success remain separate evidence. Passing historical replay does not certify arbitrary queries or regenerate unrecorded natural-language reasoning.

## Capture and frozen baselines

The shared function executor persists inputs before execution, graph snapshots at actual operator and materialization boundaries, intermediate outputs, final results, dependencies, and failures. Sealed cases bind these immutable artifacts to the original kernel, comparison contract, assessment category, and explicit result bindings. Sealing verifies input/step manifests, graph hashes and continuity, and matching completed acquisition receipts where used. Original and target captures validate the retained source documents, receipt contracts, and frozen acquisition arguments. Older cases can retain their original bytes while these exact references are checked through their immutable kernel and graph.

Function-local bindings execute through the frozen DSL. Explicit cross-call bindings consume earlier replayed outputs. Logs without those bindings are component evidence, never relabeled as complete trajectories. Missing source evidence, unavailable runtime dependencies, and model-dependent slot extraction remain explicit verification gaps. Existing legacy component replay helpers do not authorize adoption under the new policy.

## Shared adapters and real execution

The authoritative contracts are generated in the runtime reference linked below. Graph migration supports identity, type/property/relation renaming, deterministic identities from retained keys, copied-field record splits, property relocation, complete one-to-one keyed joins, and explicit relationship endpoint transformations. It rejects lost facts, missing or ambiguous keys, collisions, unsupported multiplicity, and invalid endpoints. Derived records retain source provenance and attributable derivations. Many-to-many joins and arbitrary semantic transformations remain unsupported.

Call/result adaptation reuses the existing bounded interface mappings. A package belongs to an exact parent-child revision pair and is shared by every affected case. The executor traverses the recorded ancestry iteratively and validates its endpoints. Candidate-local answers, task branches, generated Python, live services, and models are unavailable to migration programs.

Replay first reproduces each original computation, including intermediate outputs, under its pinned dependencies. It then executes current functions over the migrated original input scope and compares against the original typed result contract. Order, multiplicity, boolean/number distinctions, and absent versus null fields are preserved. A declared original multiset contract can make order irrelevant; a candidate cannot weaken that policy. Replay stops a bound trajectory at its first divergence.

Retained acquisition is an explicit input boundary. It requires the original receipt, matching arguments and capability contract, and attributable dispatch evidence. Pure operations after that boundary run again. Changed requests without matching evidence are unable to check offline. Replay never silently extracts or fetches fresh data.

## Adoption and repair

Every new revision inherits the complete protected case bank, including cases introduced by older ancestors. Later ancestor additions invalidate stale acceptance. Empty banks, partial coverage, regressions, unavailable evidence, and interruptions cannot authorize inference adoption. Construction retains the previous passing kernel. Candidate evaluation remains possible within its owned construction/development run so a failed proposal can be repaired.

The same acceptance evidence controls campaign selection, corpus promotion, UI eligibility, API job submission, and actual runtime admission. Read-only inspection checks evidence without executing work or mutating banks. Replay and Reset in the UI remain viewer controls.

First failures identify migration, schema, call/function, baseline, or verification gaps. Construction receives typed failure summaries plus the failed candidate's schema/functions, relevant original programs, and adapter structure. Expected values and task-specific arguments stay outside adapter proposal context. Repair creates another candidate and reruns the same inherited bank; it cannot remove failures or rewrite their criteria.

## Running the checks

The deterministic acceptance command uses the checksum-pinned official Coffee corpus and explicit authored schemas/functions/adapters. It persists a three-revision sequence, record split and relationship traversal, a bound trajectory, an older-only regression, and an attributable repaired candidate. Kernel eligibility evidence comes from actual HermiT and function probes.

```sh
uv run --locked python scripts/verify_historical_replay.py
```

Each invocation creates a distinct local evidence directory and prints its receipt path. Zero model and live MCP calls are checked from the actual store. Retained-weather tests separately exercise genuine acquisition receipts, changed contracts/arguments, and missing evidence.

The optional `scripts.verify_replay_proposals` command requires explicit paid execution, an existing ledger, and a spending ceiling. Model generation occurs only at proposal/repair boundaries; its receipts remain separate from zero-model regression reports. No paid outcome is established merely by the presence of that script. Actual verification receipts and limitations belong in the work-plan evidence log.
