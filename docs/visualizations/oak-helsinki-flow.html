What is actually sent to the model?
Three contexts, assembled separately
Every invocation starts fresh. Saved artifacts do not become model context unless the application includes their contents in that request. The same model is used for three different jobs.

Each call also receives the application system and launch prompts plus its stage instructions. The full exact application payloads are available at steps 2, 6 and 10. This is an audit of application-supplied context, not a provider-internal prompt dump.
Why two observation fields appear in the saved planner payload
inputs.context.observations is part of the unchanged initial context and remains []. The separate inputs.observations field is the current observation list. It changes from [] to [observation-1]. The final model receives both fields exactly as saved.

What did construction make reusable?
Construction produced the schema, typed function interfaces, operator sequences and their validation evidence. At inference, the LLM binds the query to this existing structure. It does not regenerate the schema or re-plan the filter-and-count implementation.
Native forecast arguments still look like MCP arguments because the generated acquisition step calls that same real service. The additional structure is the fixed route from acquisition through typed records to a checked result.

This MCP extension starts without forecast facts. The agent chooses F first; acquisition inside F obtains Cq, builds Gq and then continues F. The stepper describes this actual implemented route.
